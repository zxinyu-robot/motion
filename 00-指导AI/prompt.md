# 本项目 AI 开发指导 Prompt

> 本文件是**给 AI（以及协作开发者）的强制工作准则**。任何 AI 在本仓库进行设计、编码、评审、排障前，必须先阅读并遵守本文件。
> 本文件本身也严格遵循下面的七条铁律：凡是写进本文件的事实，都来自对仓库的真实扫描；凡是无法从真实文件确认的，一律标注为“推断”或“待补充”。

---

## 0. 七条铁律（最高优先级，任何情况下不得违反）

### 铁律一：不能编

版本、依赖、路径、包名、类名、函数名、调用链，**都必须来自真实文件、配置或代码使用痕迹**。

- 禁止凭"常见做法""一般项目都这样"来填写任何具体信息。
- 引用任何事实时，应能指出其来源文件与位置（路径 / 行号 / 配置项）。
- 无法从仓库中找到依据的内容，**宁可留空并标注，也不许编造**。

### 铁律二：不能只看表面

- 项目**声明**了某个依赖 ≠ 代码里**真的使用**了它 → 必须回到源码验证使用痕迹。
- 存在某个**目录名**（如 `service/`、`adapter/`）≠ 项目**真的采用**了那种架构模式 → 必须看代码实现验证。
- 存在某个配置项 ≠ 它真的被读取/生效 → 必须追踪读取点。

### 铁律三：要区分事实、推断、待补充

所有产出文档（含 `ProjectInfo.md`、设计文档、本文件的更新）必须显式区分三类信息，并分别打标：

- **【事实】**：由具体文件 / 配置 / 代码使用痕迹直接确认，附来源。
- **【推断】**：基于代码结构、命名、上下文合理推测，但未被直接证实，需说明推断依据。
- **【待补充】**：证据不足，需要人工确认或补充。



### 铁律四：不能只扫标准目录

真实项目的配置、脚本、文档、运行资源不一定放在标准位置。扫描时必须**同时检查常见与非标准目录**，至少覆盖：
`docs`、`config`、以及根目录下的隐藏文件（`.env*`、`.gitignore`、`.cursorignore` 等）。
**统筹仓例外**：本仓为架构/规划文档仓，**不含** `src/`、`docker/`、`scripts/` 等开发目录；具体实现见 `01-工作计划/技术栈索引.md` 指向的 `motion_ws/`。

### 铁律五：统筹仓与开发栈分离

- **【事实】** 本工作区（`motion/`）定位为**统筹架构仓**：按层级组织规划、设计、规范与文献文档。
- **【事实】** 可编译代码、Docker 环境、colcon 工作空间、SDK 集成等**具体开发**位于同级目录 `motion_ws/`（见 `01-工作计划/技术栈索引.md`）。
- 扫描本仓时**不得**据 `motion_ws` 内容（Dockerfile、依赖版本、clone 的第三方仓库）推断统筹层的全局技术栈事实。
- 在本仓讨论 Go2 等平台时，仅引用规划文档中的平台描述；涉及代码/环境细节须切换到 `motion_ws/`。

### 铁律六：先专利后论文

- 同一技术点若专利尚未 **filed**，不得将完整方法细节写入待投稿论文或公开 Spec。
- 标注 `confidentiality: patent-sensitive` 的文档，AI 不得建议全文公开到可检索渠道。
- 论文与专利分流表见 `06-产出/专利/专利族谱映射.md` 与汇报材料 §7.2。

### 铁律七：独立核校，不默认接受前提

- 人类输入应先区分为需求、假设、事实陈述或设计建议；**不得**因提出者身份或重复强调而自动升级为事实。
- 先找支持证据与反证，再给结论；发现事实冲突、逻辑断层、范围膨胀、隐式耦合或安全缺口时，必须直接指出。
- 结论须标注【事实】/【推断】/【设计决策】/【待补充】；关键结论附来源与验收方法。
- 证据不足时停止升级结论并标【待补充】；重大架构替换先分析问题、收益、耦合、故障模式、Benchmark 与回退路径，不得直接实施。
- 上位原则见 `项目宪章-无人协同系统工程.md`；Go2 P0 专项约束见 `02-架构设计/Go2端侧-可闭环易解释系统工程.md`。

## 2. 上位规范（本项目的既有约定，必须遵守）

本项目已有两份指导文档，AI 必须将其作为约束来源：

- `我+AI如何去完成工程项目？.md`（同目录）
- `项目开发规范准则/项目开发规范准则.md`

从中提炼出的**已确认约定【事实】**：

### 2.1 项目文档

- Python 项目：使用 `mkdocs + material` 主题编写文档。
- C++ 项目：使用 `Doxygen` 编写文档。



### 2.2 代码规范

- 重要函数须有注释，说明**参数、返回值、功能、示例**。
- 注释规范统一采用 **Google Style**（[https://zh-google-styleguide.readthedocs.io/en/latest/contents.html）。](https://zh-google-styleguide.readthedocs.io/en/latest/contents.html）。)
- 接口字段命名统一采用**大驼峰 / 小驼峰**。
- 目录结构参照文档中给出的 C++ / Python 标准模板（见 `项目开发规范准则.md`）。



### 2.3 任务标记（Todo Tree）

- 在代码中使用统一标签提醒问题：`TODO / BUG / FIXME / HACK / NOTE / TAG / DONE / TEST / UPDATE`。
- 每次协作先查看他人改动，对建议对应修复。



### 2.4 Git 工作流

- 分支模型：`master`（稳定可飞版本）、`dev`（测试）、`feature/*`（新功能）。
- 严禁在 `master` 上直接开发；严禁随意 `git push -f`。
- **永不**版本控制 `build/`、`devel/`。
- 提交信息前缀规范：`feat` / `fix` / `refactor` / `docs`。
- 开发前 `git pull --rebase`；每完成一个小功能即提交，避免一次提交大量改动。
- 面向 Jetson 本地开发 + Gitee 远端同步 + 代码安全回退，务必保证 `master` 永远可回退、可运行。



### 2.5 算法开发规范

- 流程：寻找参数 → 了解参数定义 → 对参数做数学建模转换 / 数据预处理 → 参数与算子结合形成逻辑算法。
- 注意不同模式对同一参数的处理方式可能不同。

## 3. AI 在本项目的标准工作流



### 第 1 步：先建立项目认知，再写代码

接手任何任务前，先**读懂项目**（看结构、看依赖、看调用链、看约定、看风险），而不是直接写代码。需要弄清：

1. 技术栈（语言、C++/Python、中间件、算法框架等）——**从构建文件与代码确认**。
2. 代码目录如何组织。
3. 哪些是对外接口、哪些是外部服务依赖。
4. Controller → Service → 下游 的完整调用链。
5. 配置文件、环境变量、脚本、文档分别在哪。
6. 命名约定、分层约束、开发习惯。



### 第 2 步：生成 / 更新 `ProjectInfo.md`（重点是"可信"而非"完整"）

当仓库中有真实代码后，执行深度扫描并产出 `ProjectInfo.md`，包含：

1. **项目结构深度扫描**：从根目录关键文件到源码/资源/测试/脚本/配置/文档，判断单模块还是多模块，记录**真实路径**。
2. **技术栈与依赖分析**：从构建文件（如 `CMakeLists.txt`、`pyproject.toml`、`requirements.txt` 等，以实际存在者为准）提取信息，**再回到代码验证真实使用**。
3. **代码组织与命名约定分析**：梳理各层/各包结构，识别主流命名写法。
4. **架构模式一致性验证**：验证是否真的使用了某分层/设计模式，不得只凭目录名下结论。
5. **服务调用链路分析**：从入口（REST/RPC/定时任务/消息消费/ROS 节点等真实入口）追踪到下游。
6. **架构实现分析**：总结异常处理、参数校验、返回封装、配置管理、日志监控、异步调度、容错降级等**真实实现方式**。
7. **生成并校验**：按模板输出，并在完成前校验版本、路径、接口、配置、环境变量是否与代码一致；证据不足处标 **【待补充】**。



### 第 3 步：TDD 与测试用例

- 采用 **TDD（测试驱动开发）**：先明确输入、输出，生成开发/测试用例，再实现。



### 第 4 步：编码与提交

- 遵守第 2 节的代码规范、命名规范、注释规范。
- 按第 2.4 节 Git 工作流提交，提交信息符合前缀规范。
- 对未完成/风险点，在代码中打 `TODO`/`NOTE`/`BUG` 标签。

## 4. 每次产出前的自检清单（Checklist）

在提交任何设计、代码或文档前，AI 必须逐条自检：

- [ ] 我写的每一个版本号/依赖/路径/包名/调用链，是否都能指向真实文件或代码痕迹？（铁律一）
- [ ] 我是否验证了"声明的依赖真的被使用""目录名对应的架构真的存在"？（铁律二）
- [ ] 我是否对每条信息标注了【事实】/【推断】/【待补充】？（铁律三）
- [ ] 我是否扫描了非标准目录（config/docs/隐藏文件等），而非误扫已迁出的开发栈？（铁律四）
- [ ] 我是否区分了统筹仓（本仓）与 `motion_ws/`，未将实现栈环境当作统筹层事实？（铁律五）
- [ ] 我是否遵守了本项目既有的命名、注释、Git、文档规范？（第 2 节）
- [ ] 我是否没有把任何密钥/令牌写入代码或文档？
- [ ] 我是否把人类输入中的假设、设计建议与可验证事实分开，并检查了反证或冲突？（铁律七）
- [ ] 我是否把愿景、proposal 与 measured 结论分开，且为关键结论提供来源与验收路径？
- [ ] 我是否为新增模块或技术说明了边界、失败/降级路径与可替换性，未引入未说明的隐式耦合？
- [ ] 我是否检查了专利、保密与公开边界，未泄露 `patent-sensitive` 方法细节？
