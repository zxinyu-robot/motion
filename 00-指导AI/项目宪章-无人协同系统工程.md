# motion 项目宪章：可演进的无人协同系统工程

> **定位**：本宪章定义 motion 的上位目标、工程基调、证据纪律和 AI 协作方式。它约束全平台、全阶段工作；具体协议、算法和平台实现以各层 canonical 文档为准。  
> **阅读优先级**：高。AI 或协作者在涉及项目定义、架构取舍、新技术引入、验证结论和对外表述时，须在 `ProjectState.md` 与 `00-指导AI/prompt.md` 后阅读本文。  
> **保密**：`internal`。本文仅定义原则，不包含申请前的 Token schema、事务字段、双触发阈值或权利要求级细节。

## 1. 三层项目定义

| 层级 | 定义 | 边界 |
|---|---|---|
| 上位系统工程 | **motion** 是面向持续演进的无人协同系统工程：贯通感知、空间状态、协同、决策、执行、安全和验证 | 不等同于某一 SLAM、模型、通信栈或机器人平台 |
| 产品主线 | **ForkSpatialLink** 是空间数据与任务执行中间件产品方向 | 负责空间数据契约、端边云流动、任务执行编排与弱网闭环，不替代机器人底层安全 |
| 当前 P0 验证 | **Go2** 是首个闭环验证载体；当前 **Super-LIO** 是首个 SLAM Producer | 仅是当前实现和证据入口，可在满足准入 Gate 后替换 |

**【事实】** 当前 P0 范围、Go2 单机基线和多机 Gate 的实时状态以 `ProjectState.md` 与 `40-验证/` 为准。  
**【设计决策】** 稳定的是系统目标、数据契约、验证方法与安全边界；具体 Producer、规划器、通信库和模型允许演进替换。

## 2. 项目基调

1. **系统闭环优先于单点先进**：任何能力必须进入“输入—状态—决策—执行—结果—反馈”的可观测链路。
2. **实测证据优先于方案描述**：愿景、proposal 与 measured 结论不可混用。
3. **稳定契约优先于绑定具体算法**：模块经显式接口交换数据，不允许消费者依赖 Producer 的内部可变对象。
4. **安全降级优先于理想性能**：语义或远端决策不可直接越过端侧安全边界；故障时应检测、隔离、降级与恢复。
5. **简单可解释优先于不可控复杂性**：先采用可重放、可归因的确定性机制；学习型或复杂策略须证明额外收益。
6. **新技术先证明适配，再进入主线**：新颖性不是准入依据，必须接受隔离原型和基线对照。
7. **上层规划必须向下沉淀**：活跃规划必须产生可验收的实现或验证工件；没有下层工件的输入停留在 input/analysis，不以重复扩写代替工程进展。

## 3. 最终交付定义

项目最终交付不是单篇方案文档、单段演示视频或单项算法指标，而是能够经受复核的系统成果包。每项对外或阶段性成果应同时建立以下四类证据：

| 交付维度 | 必需内容 | 最低证据形式 |
|---|---|---|
| 事实数据 | 指标、资源、网络、成功/失败结果与版本 | 原始日志、bag、配置、commit、Benchmark 报告 |
| 链路闭环 | 从输入到结果的可执行数据/控制链，含安全与降级 | 可复现步骤、端到端场景、状态/错误码与回传证据 |
| 论文逻辑 | 问题、缺口、方法边界、假设、实验设计、结论限制 | 论文 meta/outline、论证链与“主张—证据”映射 |
| 相关工作 | 可核验的对比对象、差异、复用边界与不能主张之处 | 原始论文/官方资料、阅读笔记、相关工作矩阵 |

**【设计决策】** 任何成果主张均采用以下论证链；其中任一环缺失，只能列为进行中或【待补充】，不得包装为完成成果：

```text
真实问题
  → 相关工作与差异
  → 可检验假设 / 系统设计
  → 可复现实验与链路闭环
  → 原始数据与对照
  → 受边界约束的结论
```

数据如何在各环之间持续积累与放大，见 `02-架构设计/数据飞轮-实施清单与架构.md`。

## 4. 统一术语与解释标准

| 术语 | 本项目中的定义 |
|---|---|
| 任务执行闭环 | 感知/状态 → 决策 → 执行 → 结果 → 反馈；可用于单机、多机和端边云系统 |
| 证据验证闭环 | 主张 → 可复现实验 → 原始证据 → 指标/结论 → 回链设计与状态看板 |
| 研发知识闭环 | 输入 → 分析 → 设计 → 实现 → 验证 → 沉淀 → 产出，遵循 `WORKFLOW.md` |
| 可解释 | 每个关键行为可追溯输入、状态版本、决策依据、执行过程、终态与失败原因；不等同于事后生成自然语言说明 |
| 可验证 | 结论能关联场景、版本、配置、日志、bag、指标或明确的待补充项 |
| 高内聚低耦合 | 模块只拥有本职责内状态，通过版本化契约和明确错误语义协作，不共享隐式状态或内部对象 |
| 强可靠 | 故障可检测、可隔离、可降级、可恢复；安全动作不依赖不可靠的远端链路 |

## 5. 系统工程约束

### 5.1 模块边界

每个模块或外部技术接入必须说明：

- 输入、输出和数据/状态所有权；
- 时间、会话和版本语义；
- 失败码、超时、重试和幂等策略；
- 安全边界、降级路径和恢复条件；
- 可观测指标、验证场景与替换条件。

**【设计决策】** Producer、契约与消费者应解耦。下游依赖稳定契约，不直连上游模块的内部可变状态；具体实例见 `02-架构设计/Go2端侧-可闭环易解释系统工程.md`。

### 5.2 变更与演进

架构或关键模块替换应遵循：

```text
保留旧基线 → 单变量变更 → 同场景复测
→ 收益与退化分析 → 准入、回退或继续旁路验证
```

禁止同时更换多个关键栈后直接归因。接口发生不兼容变更时，应声明版本、兼容期、迁移路径与回退条件。

### 5.3 新技术准入 Gate

新算法、论文方法、模型或中间件进入主线前，应回答：

1. 它解决哪个已被证实的问题？不引入会怎样？
2. 与既有模块是重复、互补还是替代？
3. 引入的耦合、状态、资源与故障模式是什么？
4. 能否通过适配器或旁路原型隔离？
5. 用哪个基线、场景和指标判定收益？
6. 失败后如何安全回退？
7. 是否存在许可证、专利、保密或公开披露风险？

未回答清楚时，只能进入 input/analysis 或隔离原型，不得升级为 P0 主线承诺。

## 6. 证据法与结论裁决

### 6.1 标签纪律

- **【事实】**：有可定位的原始数据、bag、日志、commit、配置、源码或文档来源。
- **【推断】**：有明确依据但未经直接证实，必须说明推断边界。
- **【设计决策】**：为达成目标而作出的当前选择，不冒充既有事实或实测结果。
- **【待补充】**：证据缺失、冲突或尚未完成验证；不得为了叙述完整而虚构。

### 6.2 冲突裁决优先级

```text
原始实测数据 / bag / 日志
  > 对应 commit 的可复现实验
  > 当前源码与配置
  > 已冻结的架构决策
  > 规划文档与愿景
```

发生冲突时，先报告冲突及其证据，不得擅自选择符合预期的一侧。

### 6.3 对外与专利边界

`patent.stage < filed` 时，不得将未申请技术点的完整方法写入待投稿论文或公开 Spec。`confidentiality: patent-sensitive` 文档不得建议公开到可检索渠道。对外材料只能使用已经允许公开且证据等级匹配的表述。

## 7. AI 作为独立技术审查视角

AI 不以“人类提出即为事实”为工作前提，而应：

1. 将人类输入识别为需求、假设、事实陈述或设计建议；
2. 先查证事实与反证，再给出结论或实现建议；
3. 主动识别前提错误、逻辑断层、范围膨胀、模块耦合、证据不足和安全缺口；
4. 在支持方案时同时说明适用边界、风险、替代路径与验证方法；
5. 证据不足时明确标注【待补充】；重大架构变更先给出 Gate 分析，不直接实施；
6. 不替代人类责任人拍板，也不把 AI 推断升级为项目事实。

建议采用“生成轮 → 独立核校轮”：核校轮逐条检查来源、证据等级、反例、范围、保密和验收条件，不以润色替代审查。

## 8. P0 首个治理样板

**【事实】** 纯 Nav2 Go2 单机基线的 N4（2 m）、N5（行走中急停）和 N6（3 m）已有狗端通过记录；bag 回传、ATE/RPE、NAV-2/NAV-4 与增量事务仍待补充，详见 `40-验证/BENCH-P0-Go2-MotionSLAM-基线.md`。最新 Go2 代码中的 SCAN-Planner hybrid 尚无对应 PASS 记录。

**【设计决策】** 以 N4/N5 与增量空间事件为首个 Gate 样板。每次测试至少回链目标、输入/空间版本、执行状态、失败码、bag/日志与 commit；核校时重点排查：

- proposal 是否被表述为 measured；
- 缓存淘汰是否被误作现实空间移除；
- “低拷贝”是否被误称为端到端零拷贝；
- 云端/网关失效时端侧安全降级是否仍成立。

只有通过 Gate 的结论才能进入知识沉淀和对外产出。
